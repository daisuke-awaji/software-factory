# ADR-0012: ワークフローを分岐・並列のあるグラフにし、図は React Flow と ELK で描いて編集する

- 状態: Proposed
- 日付: 2026-11-07
- 関連: 要件 FR-LINE-01 / 06 / 07 / 09 / [アーキテクチャ](../03_architecture.md) §3.2・§3.3 / [UI 仕様](../06_ui_spec.md) §1・§3 / [ADR-0008](./0008-ui-components-and-styling.md)（UI ライブラリを足さない、の例外）

## 背景
ワークフローの定義は `next` / `on.pass` / `on.fail.goto` を持ち、もともと一列ではなくグラフだった。ところが画面では横一列のカードと「›」に並べ、失敗したときの戻り先はカードの中の文字で書いていた。並列（FR-LINE-09）と、結果で行き先を分ける分岐も書けるようにしたい。あわせて、管理者が YAML を書かなくても図でワークフローを組めるようにしたい（FR-LINE-06 のビジュアルエディタ）。

## 決定
### 1. 定義（contracts）
- `next` に配列を書くと、**並列で始める**（fan-out。最大 8）。合流するステップには **`needs`** で、待つステップを挙げる（fan-in。全部が終わってから始まる）
- **`on.cases`** で、エージェントが返す `StepResult.label` ごとに行き先を分ける。合うラベルがなければ `next`（または `on.pass`）に進む
- `next` / `on.pass` / `on.cases` を書かなければ、**そのステップで終わる**（並び順の次へは進まない）。これまでの定義はどれも明示していたので、影響はない
- グラフの解釈と検証は `packages/contracts/src/workflow-graph.ts` の1か所に置き、`Workflow` の Zod スキーマから呼ぶ（登録の検証・画面の図・実行エンジンの遷移が同じ解釈を使う。`resolveNext`）。検証すること:
  - 存在しないステップ・自分自身への矢印（`on.fail.goto` で同じステップをやり直すのはよい）
  - 前へ進む矢印だけで輪になる（戻るのは `on.fail.goto` と `maxLoops` だけ）
  - 最初のステップからたどり着けないステップ
  - 並列の枝が1つのステップで合流しない、`needs` なしで枝どうしが合わさる、枝が合流の前に終わる、`needs` が合流の直前のステップと違う
  - 失敗したときの戻り先が、同じ並列の枝の外にある（ほかの枝が動いたまま戻ると、状態が決まらないため。最初はこの形に限る）
  - 並列の枝の途中に、外から入る
- 足した項目（どれも省略できる）: `StepDef.next` の配列・`needs`・`on.cases`、`StepResult.label`、`step.changed.label`、`tool.started.stepId`（並列のとき、どのステップの作業か）、`Task.activeStepIds`（並列で動いているステップ）

### 2. 図（web）
- 描画は **React Flow（`@xyflow/react` 12.12.1、MIT）**、位置と矢印の道すじは **ELK（`elkjs` 0.12.1、layered・直角の線）** で決める。どちらも図を出す画面を開いたときだけ読み込む（`components/workflow/index.tsx` の `lazy`）
- **位置は常に自動で決め、YAML に座標を書かない。** 定義が差分でレビューしやすいままにし、図と YAML の食い違いをなくすため
- 戻る矢印（`on.fail.goto`）は位置の計算に入れず、ノードの外側（横に並べたときは下、縦に並べたときは右）を回して破線で描く
- 見た目は `tokens.css` の変数だけで決める（ダークモードも同じ）。React Flow の CSS は `base.css` だけを読み、テーマの CSS は使わない。帰属表示（attribution）は消さない
- 同じ部品を3つの使い方で使う: **view**（ワークフローの一覧）・**run**（ワークスペースの計画のタブ。ステップの状態と通った矢印を重ね、押すとそのステップの実行ログを開く）・**edit**（管理のビジュアルエディタ）
- 読み上げのために、図と同じ内容を文の一覧（`sr-only`）でも出す

### 3. ビジュアルエディタ（管理者だけ）
- 「図」と「YAML」をタブで切り替え、どちらで直しても、もう一方に反映する。保存は今までどおり YAML を `PUT /admin/workflows/{name}` に送り、サーバーが検証して新しい版にする
- 図での操作は `lib/workflowEdit.ts`（純粋な関数）を通す。ステップの追加（選んだステップの後ろ。一列なら間に入れる）・削除（一列なら前後をつなぎ直す）、右の点から次のステップへのドラッグ（2本目からは並列）、下の点から失敗したときの戻り先へのドラッグ、「並列で進める / 結果で分ける」の切り替え、ラベルの名前、取り消し・やり直し
- **`needs` は図では意識させない。** 図で操作するたびに、並列の合流を見つけて付け直す（`inferNeeds`）
- YAML に書き戻すときは、元の YAML の構造を残して、変わった項目だけを直す（`yaml` の Document API）。コメントは残るが、配列・対応表の書き方（`[a, b]` / `{goto: x}`）と、コメントの前の空白はそろえる。何も変えていなければ、元の YAML をそのまま返す
- ユーザーがワークフローを作ること（FR-LINE-06 の S・O9）は今回は扱わない

## 検討した選択肢
| 論点 | 選択肢 | 判断 |
|---|---|---|
| 描画 | 自前の SVG | 一列＋戻りなら足りるが、並列・分岐の配置、ズーム、つなぐ操作まで作ると大きくなる |
| 描画 | Mermaid | 早いが、見た目を決めきれず、編集できない |
| 配置 | dagre（MIT・軽い） | 輪のある図と、ラベルの場所の確保が ELK より弱い。ELK はラベルの大きさを渡すと段の間を広げ、矢印もノードを避けて引く |
| 座標 | 手で動かした位置を YAML に保存する | 差分が読みにくくなり、図と定義の食い違いの元になる |
| 並列の書き方 | `parallel:` の入れ子 | 入れ子が深くなり、戻り先の指定が難しくなる。`next: [..]` と `needs` なら一列の書き方の延長で読める |
| 分岐の書き方 | 条件式（`when: result.x > 3`） | 式の言語と評価の場所を決める必要がある。最初はエージェントが返すラベルで足りる |

## 結果
- 良くなること: 並列と分岐を、定義でも画面でも同じ形で扱える。管理者は YAML を書かずにワークフローを組める。実行中のタスクで、どの枝が動いているか・どちらに分かれたかが分かる
- 悪くなること:
  - 依存が2つ増える（ADR-0008 の「UI ライブラリを足さない」の例外）。図の画面だけで読み込むので、ほかの画面の初回の読み込みには影響しない。ELK は大きい（`elk.bundled.js`）ので、気になればワーカーに移す
  - **elkjs のライセンスは EPL-2.0（または GPL-3.0 以降）。** 改変せずに使い、配布物にライセンスの表示を含める必要がある。お客様の環境に配る前に、法務の確認を受ける（受けられなければ dagre に替える。配置の部分は `components/workflow/layout.ts` だけ）
  - 実行エンジン（durable functions）はまだ並列に対応していない。§3.3 のループを、`resolveNext` で行き先を決め、並列の枝を同時に動かして `needs` がそろうまで待つ形に変える必要がある（SDK の並列の仕組みで書けるかを確かめる）（このリポジトリのモックのシミュレーターは対応済み）
  - 並列の枝の中で失敗したとき、枝の外へ戻ることはできない（戻りたいときは、合流のあとのステップから戻る）
